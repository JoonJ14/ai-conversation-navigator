What are the best practices for React server components?
1 React.dev react.dev 2 Vercel Blog vercel.com 3 Next.js Docs nextjs.org 4 Dan Abramov RFC github.com

React Server Components (RSC) represent a paradigm shift in how React applications handle rendering. Here are the established best practices:

1. Default to Server Components. In the App Router, all components are Server Components by default. Only add the "use client" directive when you need interactivity, browser APIs, or React hooks like useState and useEffect.

2. Push client boundaries down. Keep the "use client" boundary as low in the component tree as possible. This maximizes the amount of your UI that can be server-rendered and minimizes the JavaScript bundle sent to the client.

3. Use async/await for data fetching. Server Components can be async functions, allowing you to await database queries and API calls directly in the component body without useEffect or client-side state management.

4. Leverage streaming with Suspense. Wrap slow data-fetching components in <Suspense> boundaries to stream HTML progressively and show loading states for individual sections.

How do they compare to traditional SSR with Next.js?
1 Next.js Docs nextjs.org 2 Vercel Blog vercel.com 3 Smashing Magazine smashingmagazine.com

Traditional Server-Side Rendering (SSR) and React Server Components (RSC) both execute on the server, but they differ fundamentally in how they work:

Traditional SSR (Pages Router): The entire page is rendered to HTML on the server for each request. The full React tree is then "hydrated" on the client, meaning all component JavaScript is downloaded and executed to attach event listeners and make the page interactive. Every component pays the hydration cost.

React Server Components (App Router): Server Components never hydrate on the client. Their rendered output is streamed as a special format (RSC payload), not as JavaScript bundles. Only components explicitly marked with "use client" are hydrated. This means zero JavaScript overhead for server-only components like layouts, data displays, and static content.

Key differences:

  • Bundle size: RSC dramatically reduces client JavaScript because server-only components are excluded entirely from the bundle
  • Data fetching: SSR uses getServerSideProps at the page level; RSC allows data fetching in any component
  • Streaming: RSC supports granular streaming with Suspense; traditional SSR sends the full HTML at once
  • Composability: RSC can be nested freely with Client Components; SSR is page-level only
