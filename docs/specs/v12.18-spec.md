## Claude

**Baseline (DEC-060), required:**

- **Compaction awareness:**
  - **Effective context.** Read `compaction_summary` from the payload the index already downloads. Effective context = the overhead, plus the last summary's characters ÷ 4, plus everything after the message that carries it. The meter's percentage, the dots and the label all use the effective context. The whole-history figure moves to a tooltip or a secondary line ("whole chat ~620K").
  - **"Summarized N×"** in the meter, where N is the number of summary markers on the active path.
  - **A notice on a new summary.** When N grows on a refetch within the open page: "Claude summarized earlier messages at Q#n. Context is now ~X. Q#1–(n−1) are kept as a summary." It's dismissible and not kept after a reload.
  - **Navigate.** Questions before the last summary point carry a small "summary" tag, with a divider at that point ("Summarized above · word for word below"). This applies to Navigate's list only, not to Search or the exports.
- **The change notice.**
  - Detection: the previous `_ciModel` against the new one, for the same conversation, within the open page.
  - Text: "Model changed: Opus 5 → Opus 4.8. Window 1M → 500K, so 35% → 71%."
  - When the effective context exceeds the new window, add "Claude will summarize earlier messages to make room."
  - It's dismissible and not kept after a reload. Switching conversations is not a model change.

**Display A:** the existing percentage bar, plus the label "<model> · <window> window" under it.

- The display names come from a small table of model ids (claude-opus-4-8 → "Opus 4.8"). An unknown id shows as the raw id.
- Wording: "limit assumed" appears ONLY when the model can't be identified at all. A known model outside the Help Center's 1M and 500K lists (Opus 3, for example) is a plain 200K, with no "assumed".

**Fallback alert.** With no summary marker on the path, an effective context at or above 95% of the window shows: "This chat has likely passed its context window. If code execution is on, Claude summarizes earlier messages to continue, so early details may be lost; without it, the chat stops at the limit."

## ChatGPT (owner's decision: a plan setting)

- **The setting.** "ChatGPT plan": Not set (the default) / Free / Go / Plus / Pro.
  - It lives in the navigator's settings, with a small "<plan> · change" control on the ChatGPT meter that opens it.
  - It's never guessed or detected. The navigator trusts the last value picked.
- **Windows.** From chatgpt.com/pricing (read 2026-11-04; cite it in a code comment), by plan and mode:

  | Mode | Free | Go | Plus | Pro |
  |---|---|---|---|---|
  | Instant | 27K | 54K | 54K | 128K |

  Note the pricing page's caveat that the space for your input is smaller than the total. "Varies", an unknown mode, or an unset plan means **no percentage**.
- **Display.**
  - With a plan and a known mode: the percentage bar, plus "<mode> · <window> window (<plan>)".
  - Otherwise: "~X tokens (est.) · window depends on your plan" and the "set your plan" control.

- **The change notice** fires when the latest answer's mode changes the window, for example from Instant 54K to Thinking 256K, or when the plan setting changes.
- **Fallback alert** at 95% or more, with no marker: "This chat has likely passed its context window. ChatGPT may drop or summarize earlier messages."

Each dot's colour reflects the chat's estimated size up to that question, against a **1M-token reference**, with the bar's thresholds: green below 70% (700K), yellow below 85% (850K), red from 850K on. This replaces today's colours by position out of 40.

# Part 2 — ChatGPT answer bookmarks on "fallback" turns

**The bug** (ROADMAP 13; measured live, Chrome, 2026-11-01):
- A ChatGPT turn with two shown text nodes can render the first as its own unit, with no question (`data-turn-key="fallback-turn-0"`; Q45 of the 49-question chat `69a0c6f8`).
- That unit names the FIRST node's id, while the index keys the answer by the turn's LAST node.
- So a flag there saves under an id the index doesn't list, and reads "A#?". Search already maps it through `_ix.answerIdOf`; bookmarks don't.

**First, confirm status (code, read-only).** Report on both:
- Is this bug still present on main?
- Do Claude's bookmark jumps (`_bmJumpToAnswer`, and `orbScrollToBookmark`'s uuid path) still end in an unchecked smooth glide? If yes and it's small, land them through `ciLandSettled` / `orbLandIn` here. If not small, log it and tell me.

**The fix:**
- A ChatGPT answer flag resolves its key through `_ix.answerIdOf`, so every shown unit of a turn maps to the ONE answer key. When both units are mounted, they show the same lit state and toggle the same bookmark, never two records.
- Existing records under a first-node id resolve at read time through `_ix.answerIdOf`, and are rewritten to the canonical key through `acnUpdateValue`, with no loss and no duplicates.
- A record whose id the index doesn't know stays "A#?".

**The gate** (must fail on v12.17). Use the ChatGPT windowed mock with a fallback unit matching the live markup:
- A flag on the fallback unit saves under the canonical key and reads "Answer to Q#n".
- A seeded legacy record binds.
- Both units mounted give one bookmark.
- The jump lands.

**Live test:** Q45's fallback unit on the 49-question chat. Bookmark it, check that it reads "Answer to Q#45", and jump to it from far away. Delete the test bookmark afterwards.
